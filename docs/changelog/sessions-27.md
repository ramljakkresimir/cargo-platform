# Implemented Features — Session 27

### Session 27 — 2026-09-04

#### Home page: redesigned "how it works" section (`U tri koraka do prijevoznika`)

**Previous state:** the three-step explainer on `HomePage.tsx` was a bare `.steps-grid` — three centered `{number, title}` pairs, no heading, no illustration. Separately, the hero heading (`Pronađite prijevoz ili teret na svojoj ruti`) did not share the page's left content edge with the rest of the home page (`.hero-content` used its own `padding: 0 72px` with no `max-width`/`margin:auto` centering, while `.steps-section`/`.recent-listings-section`/`.features-section` all already shared one convention: 96px/20px outer padding wrapping a `max-width:1200px; margin:0 auto` inner container).

**Design handoffs, both delivered as Claude Design/`.dc.html` prototypes read from the Desktop and reimplemented (not pasted) using the project's own tokens, fonts, and layout system:**
1. A desktop-only handoff (`design_handoff_kako_funkcionira/`) — three-column layout with a per-step UI-mockup illustration (choice toggle, route card with a floating `18 t` weight chip, price-offer rows), numbered badges, and dotted curved connectors between columns.
2. A follow-up mobile/tablet handoff (`Kako funkcionira - mobitel.dc.html`) — a vertical numbered timeline (badge + dashed connector line down the left, title + the same illustration mockups full-width on the right), with step 3 ending in a full-width solid dark CTA button instead of the desktop's small floating chip.

**Color/typography mapping (per both handoffs' explicit "map to the project's own palette, don't copy hex" instruction):** every blue in the prototypes (`#1d4ed8`, `#e6ecfb`, `#b8c3e0`) maps to the project's existing `--color-blue` / `--color-blue-soft` / `--color-blue-border-soft` tokens (the last already an established "muted blue border" token, a near-exact match for the prototype's connector grey-blue); the mobile CTA button's `#0d1330` maps to the project's own existing solid-dark button color `#14161a` (already used by `.src-btn-dark`/`.hero`, not a new value). No Manrope/DM Sans fonts were added — the home page already loads its own `Source Sans 3` font (`.homepage` class).

**Desktop implementation:** `.step-illustration` (240px-tall flex-centered box) holds a `.step-connector` SVG plus one of three new mock-card variants (`.step-mock-choice`, `.step-mock-route`, `.step-mock-offers`), reusing `--radius-lg`/`--shadow-card`/`--shadow-hover-blue`. The connectors are the one piece that took two passes: the first version anchored a fixed 64px SVG to the 32px CSS grid-gap only, which left it stopping in the empty margin well short of the actual (much wider, viewport-dependent) card edges. Fixed with a closed-form `calc()` derived from the grid geometry — since all three `1fr` columns are equal width `W` and each card is centered at a fixed `max-width:220px`, a card's right edge is always at `50% + 110px` of its own column and the next card's left edge is always reachable via `width: calc(100% - 188px)` (`188 = 220 − 32`gap) — so the dotted line spans exactly card-edge-to-card-edge at *any* desktop width with no measurement/JS, and by construction never renders under a card. Verified pixel-exact (`getBoundingClientRect`) at 1024/1440/1920px.

**Tablet/mobile implementation:** a new `.steps-mobile-list` (hidden on desktop) renders the vertical-timeline markup, reusing the same `.step-mock-*`/`.choice-row`/`.route-*`/`.offer-*` classes built for desktop (only the outer scaffold — `.steps-mobile-track`/`.steps-mobile-badge`/`.steps-mobile-line`/`.steps-mobile-content`/`.steps-mobile-cta-button` — is new). The layout switch (`.steps-grid` ↔ `.steps-mobile-list`) uses the project's existing tablet/desktop boundary (`max-width: 1023px` / desktop starts at `1024px`, already established at `index.css:1709` and `:2313` for the search and detail pages) rather than the home page's own pre-existing 768px cutoff, per explicit instruction to treat tablet the same as mobile. This surfaced a real alignment regression during verification: `.steps-section`'s own horizontal padding had to stay pinned to the *existing* 768px breakpoint (so it keeps matching `.hero-content`/`.recent-listings-section` at tablet widths, 769–1023px) even though the grid↔timeline *layout* switches at 1024px — otherwise the section's left edge would drift to the mobile 20px padding a full breakpoint tier before the sections around it. With that split, alignment of `Pronađite prijevoz ili teret na svojoj ruti` / `U tri koraka do prijevoznika` / `Najnoviji tereti` was verified pixel-exact at every tested width (375/900/1023/1024/1440/1920px).

**Hero alignment fix:** added one wrapper, `.hero-content-container { width:100%; max-width:1200px; margin:0 auto; }`, inside the existing `.hero-content` (whose padding was also corrected from `72px` to the shared `96px`), so the hero heading now sits on the exact same left edge as the rest of the page's sections, without touching `.hero-content-inner`'s intentional 760px reading-width cap.

**`KAKO FUNKCIONIRA` eyebrow:** present in both prototype handoffs; deliberately never rendered, per explicit instruction, on desktop or tablet/mobile.

**Verification performed:** `tsc -b --noEmit` and `eslint` clean on both changed files (`frontend/src/pages/HomePage.tsx`, `frontend/src/index.css` — no other files touched). Live-verified via a headless Chromium/CDP script (the Chrome extension wasn't connected either session) driving the real dev stack (frontend + backend + local Postgres) at six widths (375/900/1023/1024/1440/1920px): left-edge alignment of the three key headings, connector card-edge-to-card-edge geometry, `.steps-grid`/`.steps-mobile-list` visibility toggling exactly at the 1024px boundary, absence of `KAKO FUNKCIONIRA` anywhere in the rendered page, and no horizontal overflow at any width.
