# Implemented Features — Session 24

### Session 24 — 2026-08-27

#### Feature: User ratings ("Ocijeni korisnika")

Registered users can now rate other users 1–5 stars, with the resulting average (+ count) shown as a reusable star widget below the user's name on their own profile, on cargo/vehicle listing detail pages (rating of the poster), and on cargo/vehicle search result cards. Replaces the previous total absence of any trust signal beyond company profile fields and Session 23's chat.

**Design decisions:**
- **One rating per (rater, ratedUser) pair, not per listing.** Rating the same person again updates the existing row rather than creating a new one — mirrors `Conversation`'s "one thread per user pair" model from Session 23. This app has no "completed transaction" concept to key a per-listing review off of, so a per-pair model (with the listing recorded only as optional display context, exactly like `Conversation.cargoPostId`/`vehiclePostId`) was the better fit than a per-transaction review model.
- **Average is computed on read, not denormalized on `User`.** A `ratings` table is the sole source of truth; summary endpoints run `AVG`/`COUNT` (batched via `GROUP BY ... IN (:...userIds)` for search cards, the same shape `POST /cities/distances` already uses). Unlike `CityDistance` (an immutable cached fact), a rating average changes on every write, and read volume here — one batched query per search page load — doesn't justify the added write-path complexity of keeping a denormalized column in sync.
- **Both `raterId` and `ratedUserId` FKs use `onDelete: 'CASCADE'`**, unlike `Conversation`'s `userAId`/`userBId`, which are deliberately `NO ACTION` (a stray `CASCADE` there could ripple through a shared conversation row and delete a *third* user's messages). A `Rating` row has no such transitive risk — deleting a user only ever removes rows where that user is the rater or the rated user, nothing cascades further. This means **`AdminService.deleteUser()` required zero code changes** — Postgres handles it automatically. Verified live: promoted a disposable test account to admin, used it to delete another test account that had an active rating between them, and confirmed via direct SQL query that the `ratings` row was gone with no FK violation.
- **Half-star rendering uses a CSS partial-fill overlay** (two stacked 5-star rows, the gold one clipped to `{average/5*100}%` width), not rounding to the nearest half-star — keeps the star art exactly in sync with the adjacent numeric label (e.g. "4.3") with no lookup table.
- **Submission UI is an inline expandable panel** inside the existing `#kontakt` contact card on `CargoDetailPage`/`VehicleDetailPage` (toggled by local `useState`, same pattern the page already uses for its edit form) — no new modal primitive, since none exists in this codebase.

**Backend — new module `backend/src/ratings/`:**
- `rating.entity.ts` — `Rating` entity: `id`, `raterId`/`ratedUserId` (indexed, `@ManyToOne(User, { onDelete: 'CASCADE' })`), `score` (smallint, 1–5), `cargoPostId`/`vehiclePostId` (nullable, `onDelete: 'SET NULL'`, display context only), `createdAt`/`updatedAt`. `@Unique(['raterId', 'ratedUserId'])`.
- `dto/rate-user.dto.ts`, `dto/rating-summaries.dto.ts` — `class-validator` DTOs; the summaries DTO mirrors `CityDistancePairsDto`'s array-of-ids shape.
- `ratings.service.ts` (`RatingsService`) — `submitOrUpdate()` (self-rating rejection, 404 on unknown rated user, best-effort listing-context resolution copied from `ConversationsService.startOrGet()`, find-or-create with the same race-safe `try { save(create(...)) } catch { findOneOrFail(...) }` idiom used by `ConversationsService`/`CityDistanceService`, "attach listing context only if empty" on update); `getSummary()`/`getSummaries()` (AVG/COUNT aggregation, `average: null` — never `0` — for zero ratings, one result per requested id even with zero rows, same contract as `CityDistanceService.getDistances()`); `getMyRatingFor()` (pre-fills the picker with the caller's existing score).
- `ratings.controller.ts` (`RatingsController`) — `POST /ratings` (JWT-protected), `POST /ratings/summaries` (public, batched), `GET /ratings/user/:userId/summary` (public), `GET /ratings/user/:userId/mine` (JWT-protected).
- `ratings.module.ts` — registered in `entities.ts` and `app.module.ts`, same shape as `MessagingModule`.
- Migration `1787841599692-AddRatings` — generated via `migration:generate`, reviewed, and applied; creates `ratings` with both user FKs `ON DELETE CASCADE`, both listing FKs `ON DELETE SET NULL`, unique constraint and indexes on the user FK columns.
- Tests — `ratings.service.spec.ts` (13 tests), following `conversations.service.spec.ts`'s exact conventions (no `@nestjs/testing`, plain mock repos, `makeQueryBuilderMock()`, local fixture factory): self-rating short-circuit, unknown-user 404, create-on-first-submission, update-not-duplicate on re-rating, the save-throws race fallback, listing-context attach/drop, zero/single/multi-rating average precision, batch summaries always returning one entry per id, `getMyRatingFor` both branches.

**Frontend:**
- `components/Icons.tsx` — added `StarIcon` (outline) and `StarFilledIcon` (filled, following the existing `MoreIcon` filled-icon precedent), both using the shared `IconProps`.
- `components/RatingStars.tsx` (new) — reusable read-only display: gray 5-star base + gold overlay clipped to the exact fractional average; `role="img"` with a full Croatian `aria-label` (e.g. "Ocjena 4.3 od 5 zvjezdica (12)"); shows "Još nema ocjena" instead of an all-gray row when there are no ratings yet, so zero ratings never misreads as "worst possible score."
- `components/RatingPicker.tsx` (new) — accessible submission input: `role="radiogroup"` of five native `<button role="radio">`s (keyboard-operable for free), hover preview.
- `services/ratings.service.ts`, `hooks/useRatingSummaries.ts` — the latter a near-verbatim port of `useCityDistances.ts` for batching the search-card rating lookups into one `POST /ratings/summaries` call per page load.
- `types/index.ts` — added `RatingSummary`/`Rating` as sibling interfaces (not merged into `User`), matching how `Conversation`/`ChatMessage` were added in Session 23.
- `index.css` — new `--color-star-filled`/`--color-star-empty` tokens and `.rating-stars*`/`.rating-picker*`/`.rating-submit-panel` classes, following the existing `.src-*`/`.detail-*` naming convention; no dark-mode handling (the app has none anywhere).
- `pages/ProfilePage.tsx` — added the user's name and a `RatingStars` row between the `<h1>` and the existing subtitle (the page previously showed no name heading at all).
- `pages/CargoDetailPage.tsx` / `pages/VehicleDetailPage.tsx` — the `#kontakt` contact card now shows the poster's `RatingStars` under the company name, plus an "Ocijeni korisnika" button beside "Pošalji poruku" (same `isOwner` guard) that toggles a `rating-submit-panel` containing `RatingPicker` and a submit action; submitting refetches the summary so the displayed average updates immediately.
- `components/search/types.ts` / `components/search/ResultCard.tsx` — `ResultCardData` gained an optional `ratingSummary`; the card shows a compact `RatingStars` under the company sub-line when the poster has at least one rating (purely decorative, no new interactive element on cards).
- `pages/CargoListPage.tsx` / `pages/VehicleListPage.tsx` — wired `useRatingSummaries()` alongside the existing `useCityDistances()` call and passed the result into each card's `ratingSummary` field.

**Verification performed:** `tsc --noEmit`/`nest build` (backend) and `tsc -b`/`vite build` (frontend) clean; `npm run lint` clean on both workspaces (0 errors/warnings); `npx jest` — 12 suites / 107 tests passing (up from 11/94, the 13 new `ratings.service.spec.ts` tests). Live verification against the real backend and local Postgres with two disposable test accounts: self-rating rejected with 400; rating a user then rating them again returned the *same* row id with the score updated (not a duplicate), confirmed via `GET /ratings/user/:id/mine`; `POST /ratings/summaries` (no auth header) correctly returned `average: 2, count: 1` for the rated user and `average: null, count: 0` for an unrated one; promoted one test account to admin and used the real `DELETE /admin/users/:id` endpoint to delete the other (rater) account — the request succeeded with no FK violation, and a direct database query confirmed the `ratings` row was gone automatically, proving the `CASCADE` FK choice works in practice and that `AdminService.deleteUser()` genuinely needed no code change. All disposable test accounts and verification scripts were removed after testing.
